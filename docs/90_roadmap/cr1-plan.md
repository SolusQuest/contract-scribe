# CR1 — Adopt SolusAgent for the Documentation Scribe

> **Status:** Q1 selected the integration contract; CR1-I1 replaces the production loop and its consumers with that mapping. Current-head tests and required Ubuntu payload/Action CI establish acceptance. This migration does not complete M7 or authorize a release.

## Outcome and boundary

Replace the general agent execution machinery with an exactly pinned, published SolusAgent internal package set. ContractScribe continues to own the narrow Documentation Scribe role, scoped instructions and evidence, semantic/read tools, proposal and skip validation, campaign policy and persistence, deterministic patching and GitHub publication. CLI remains the composition root. No model capability receives mutation, state-store, credential, shell or publication authority.

CR1 runs alongside [M7](m7-plan.md). It replaces the current execution foundation without requiring M7 to finish on the old runtime. It does not complete M7's multi-target shared conversation, cumulative candidate, lifecycle or automatic-continuation outcomes. CR1 preserves the invocation-budget and dispatch-accounting behavior already implemented by M7-C4 (#216); only remaining, unimplemented M7 capabilities stay with their existing owners. Historical M3–M6 and completed M7 acceptance remain bound to their original revisions.

Use public SolusAgent APIs and consistent exact direct package pins. Keep concrete runtime/provider construction at startup; retain `ContractScribe.Agent` for the Scribe-specific adapter. Core remains free of concrete runtime/provider dependencies. Existing project/reference and capability tests must be adapted to the actual new boundary, not removed wholesale. No new assembly is justified solely by package names, and no second general loop remains in production after cutover.

## Delivery outcomes

CR1 needs no coordination parent or separate tracker. The milestone, this plan and the two outcome contracts provide its scope, dependency and acceptance view.

1. **CR1-Q1 — Establish the supported SolusAgent integration contract.** Produce an evidence-backed package/API selection and Scribe mapping, with the real producer/consumer constraints exercised through existing deterministic seams where source inspection is insufficient. This is a bounded decision/qualification outcome, independently useful even if it identifies a specific upstream gap. A passing result selects a published version and makes the implementation contract ready; a blocked result names the upstream owner, missing contract and acceptance evidence without claiming the migration is ready.
2. **CR1-I1 — Run the production Documentation Scribe on SolusAgent.** Once a passing Q1 result and its required published dependencies exist, replace the old loop, integrate product-owned tools/accounting/acceptance and migrate the actual CLI, campaign and evaluation consumers in one coherent implementation PR. Include tests, affected contracts/docs and actual packaged CLI/Action validation in that outcome. Q1 is merged and its selected published dependencies are available; I1 is agent-ready.

The separate Q1 outcome prevents implementation from assuming an unsupported provider/schema/capacity contract. A source-only decision that is already proved should not grow a new certification framework. Q1 uses at most one focused contract/qualification PR; I1 uses one coherent implementation PR. There is no extra cleanup or validation issue whose sole purpose is making an otherwise incomplete cutover usable.

The essential chain is Q1's passing result and available dependencies → I1 → runtime-dependent M7 work. Q1 may prepare independent boundary checks together; partial qualification is not enough to start the cutover. Independent M7 GitHub/lifecycle work keeps its existing prerequisites. Low migration parallelism is justified by the single runtime cutover and the unresolved predecessor contract, not by shared file names alone.

## Q1 selected integration contract

The production package set selected for CR1-I1 is `SolusAgent.Api`, `SolusAgent.Tools.Api`, `SolusAgent.Runtime.Api` and `SolusAgent.Runtime`, each exactly pinned to `0.1.0-internal.3`. Historical Q1 qualification restored and inspected the optional `SolusAgent.Providers.DeepSeek` at the same version; it is absent from the replacement production graph. Its fixed model is not equivalent to the current `deepseek-v4-flash` profile. No source-built package or older install proof substitutes for the published registry dependency.

| Surface | Selected mapping |
| --- | --- |
| Instructions and evidence | Retain the current deterministic Scribe prompt builder and ordered wire messages. Fixed Host policy stays separate from repository/context/evidence data. Reconstruct typed prompt inputs from classified runtime data and validate them against the admitted product request. |
| Tools | Keep the original model-facing schemas, including the CLI-bound scope enum, and the real product codecs/ports. An explicit bounded string envelope carries exact argument/result JSON through the runtime; no validating schema keywords are removed. Runtime tool names use collision-free registry-ordinal aliases within the public identifier grammar, while original product operation IDs remain in wire/history commitments. Complete effect-free product preparation precedes tool invocation; port-owned range/scope checks retain their existing invocation timing. Reject duplicate or invalid dynamic evidence and conflicting metadata; publish active evidence and tool history only after the complete batch passes, retaining incurred charges on later failure. Concrete read capabilities and source-bound evidence filtering remain authoritative. |
| Provider and continuation | Use a Scribe-specific public `ModelProvider` calling the existing scoped HTTP exchange. Preserve model, endpoint/profile, output-token field and exact bounded assistant continuation. Current transport continuation remains private product exchange metadata, reset on a product retry; this does not enable durable runtime conversation restoration. |
| Candidate acceptance | Convert the structured terminal tool payload to a runtime Final candidate. The Host performs the existing TerminalSubmission admission/tool debit/completion and independent Core proposal/skip validation. Preserve product budget, timeout and cancellation priority, including the difference between exhausted request capacity and tied retry exhaustion. Invalid singleton output is Reject + End with the current failure; no new repair policy is introduced. |
| Dispatch and closure | The scoped physical exchange alone owns the logical-request commitment, durable reservation/readback, physical dispatch and mandatory settlement. Library hooks acknowledge only Volatile orchestration. Track and drain the real provider operation before product completion, retirement or further effects, including after a runtime cut; failed or unknown settlement fails closed. |
| Retry and recovery | Solus owns retry admission; C4 owns persisted RetryWait and remaining-wait recovery, with library delay disabled. Keep cumulative product attempt numbering and current-execution request ordinals distinct from library correlations. Advance the product attempt/epoch and reset active tool/evidence/continuation history only when the next retry is admitted and its durable wait completes; a failure observation alone does not advance them. Scope runtime tool-call IDs to their physical response while preserving original provider IDs in product/wire commitments, so a fresh product attempt can reuse an ID safely. Recover validated business progress into a fresh Host/runtime, without restoring or recharging conversations. |
| Usage | Preserve nullable input/output, cache-read, uncached and reasoning observations. Reasoning is an output subset; unknown values are not zero or inferred from a peer. The existing C4 exposure, cost and restored-history accounting remain the product authority. |

Use explicit capacities sufficient for the accepted role: 128 retained attempts and effective retry permission up to 128, 2048 records/inputs, 256 MiB retained runtime bytes, 32 MiB text, 128 MiB aggregate provider requests, 8 MiB aggregate responses and tool envelopes, and a 1 MiB candidate. Existing product bounds still apply first, including 4 MiB prompt blocks, 32 MiB logical requests, 1 MiB artifacts, 1024 total tool calls and 16 calls per response. These ceilings are not simultaneous promised payload sizes. Per-request output is bounded by the remaining product and invocation allowances and the existing physical-request cap. Smaller library defaults remain unchanged.
